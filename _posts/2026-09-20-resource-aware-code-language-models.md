> 这篇把 CPU 周期、内存峰值、IO 延迟编码为特殊 token 融入训练，让模型在生成代码时隐式考虑资源约束——
> 等于给代码模型装上了「物理世界感知」，对边缘端代码生成和嵌入式 Agent 意义重大。

---

## 现有代码模型的盲区：活在无重量世界里

训练代码 LLM 时，喂的是源码，优化的目标是「下一个 token 预测准确」。

这产生了一个根本性的偏差：**模型不知道它写的代码会消耗多少资源**。

现实编程里，资源约束无处不在：
- 「这个函数要在 50ms 内返回结果」
- 「解析器的内存占用不能超过 2MB」
- 「这个任务要跑在嵌入式设备上，CPU 周期有限」

但代码模型在训练时从未见过这些约束，所以它的输出只能在「功能正确性」上优化，对「是否满足资源预算」完全盲。

---

## 核心方法：资源语义作为 First-Class Token

这篇文章的思路是：**把运行时资源信息当成特殊的 token 加入训练词表**。

### 训练阶段

在标准代码 token 序列中嵌入资源描述 token：

```
def parse(input_str):    <CPU:45ms> <MEM:1.2MB> <IO:na>
    # implementation
```

这些资源 token 不是注释，而是模型训练的监督信号的一部分——模型同时学习：
1. 在给定自然语言指令时生成代码
2. 在给定资源约束时生成满足该约束的代码

### 推理阶段

用户可以用自然语言加资源约束：

```
「实现一个 CSV 解析器，要求 <CPU:50ms> <MEM:2MB>」
```

模型不是「先写代码，再检查是否满足约束」，而是**在生成过程中就以资源约束为条件**——约束从外部后验变成内部先验。

## 和已有方向的区别

这个方向之前有两条相关线路，但本质不同：

| 已有方向 | 这篇的区别 |
|---------|-----------|
| **Cost-Aware Scheduling**：运行时给 agent 加资源约束 | 资源约束焊进模型权重，不是外部限制 |
| **Runtime Contract**：执行时验证资源使用 | 模型**生成时就隐式考虑**资源，不是事后验证 |
| **Post-training 过滤**：训练后去掉资源不达标的输出 | 从预训练阶段就让资源语义进入模型 |

这是一种「物理世界感知预训练」——不是给模型加脚手架，而是让模型从根本上对资源有感知。

---

## 为什么对边缘端 Agent 关键

边缘端（嵌入式、IoT、移动端）代码生成面临一个不可能三角：

- **延迟敏感**：响应必须在硬实时约束内完成
- **内存敏感**：可用的 RAM/Flash 极为有限
- **计算敏感**：CPU 主频低，没有 GPU 加速

现有代码模型在这些场景下输出的代码可能功能正确，但资源使用完全不可控——可能用了 O(n²) 算法、可能开了大数组、可能频繁触发 GC。

有了资源感知词表，模型至少有机会学会「在有限资源下选择更轻量的实现路径」。

---

## 批评性解读

**资源 token 的标注成本是主要瓶颈**。给训练数据打 CPU 周期、内存峰值标签需要大量基准测试，不是从源码能直接推断出来的。这个标注开销可能严重限制训练数据规模。

**资源测量本身有噪声**。同一段代码在不同硬件上测出的资源消耗差异巨大——`<CPU:50ms>` 指的是哪个设备上的 50ms？如果不控制硬件环境，资源 token 的语义是模糊的。

**功能正确性和资源约束可能冲突**。在某些情况下，满足资源约束的唯一方式是放弃某些功能——模型如何在生成时做这个取舍？这需要一个比「加约束 token」更精细的决策机制。

**工业界可能更倾向于「外部资源估算器 + 约束注入」**，而不是改预训练。这个方向落地的前提是资源 token 带来的效果提升足以覆盖训练成本。
