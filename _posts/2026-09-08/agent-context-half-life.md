## 问题的真实形状

大多数关于 Agent 长会话的讨论都集中在"上下文变长"——token 数量增加、context window 告急。但这个框架掩盖了更根本的问题：**上下文不是变长就完事了，它在以不同速率"老化"**。

工具返回结果会过时（CI 运行完了、PR 合入了、DB schema 变了）。用户的纠正会改变 Agent 的推理前提。环境状态在不断迁移。而 Agent 普遍的做法是把所有历史 context 一视同仁地塞进 prompt——这相当于把 Redis 缓存和只读快照放在同一个内存空间里按LRU处理。

这篇论文提出用"**上下文半衰期**"（Context Half-Life）来描述这个问题，并建议把记忆分成三层：

- **热层（Hot）**：当前任务最相关的信息，衰减最慢
- **温层（Warm）**：近期交互，衰减速率中等
- **冷层（Cold）**：历史会话，需要回溯原始信源

## 衰减的驱动因素

不是时间本身让上下文变老，而是三类"**状态迁移事件**"：

| 老化来源 | 典型场景 | 隐蔽性 |
|---------|---------|--------|
| **工具返回老化** | CI 从 FAIL 变成 PASS，但 Agent 不知道 | 高——Agent 不会主动 re-fetch |
| **环境状态迁移** | 分支合并了、schema 变更了、部署了新版本 | 中——需要显式同步 |
| **用户纠正** | 用户说"不是这样做"，改变了任务前提 | 高——历史推理路径被否定 |

CI 日志、PR 状态、DB schema、已合入的代码——这些都是**外部真值**，但 Agent 倾向于相信"记忆里的版本"而不是去 re-check。这种行为模式在短任务里无害，在长会话里是 bug 的温床。

## 对软件工程实践的冲击

如果"Agent 记忆力应该被设计成缓存系统"，那么工程实践需要三个转变：

**1. 工具调用需要声明式失效条件**

不是"调用 tool X"，而是"调用 tool X，条件是如果 Y 状态发生变化则自动失效"。类似 HTTP 的 `ETag` + `If-None-Match` 机制。

**2. 外部状态需要主动轮询或订阅，而非一次性获取**

长会话 Agent 应该持有对关键外部状态（CI 状态、PR 状态、schema 版本）的轻量级引用，而不是在会话开始时 snapshot 一下就再也不管了。

**3. 上下文窗口应该按价值分层，而不是按时间**

现在的普遍做法是 FIFO（最早的信息先被挤出）。更合理的策略是按"信息可验证性"和"状态依赖性"来管理——一个已合入的 PR 比 100 条中间推理步骤更值得保留。

## 形式化描述

论文定义**上下文半衰期**为：在当前 session 下，给定上下文片段 `c` 在被用于决策时仍然"有效"的概率降至 50% 所需的时间。形式化为：

```
HL(c) = argmin_t { P(valid(c, t) = true | t) ≤ 0.5 }
```

其中 `valid(c, t)` 由三个独立衰减因子共同决定：

```
P_valid(c,t) = P_tool(c,t) × P_env(c,t) × P_user(c,t)
```

三个因子分别建模为指数衰减，衰减率由环境变化频率和任务类型共同决定。

## 真正的问题意识

这篇论文（思想框架）的核心贡献不是提出了一个新概念，而是把一个问题从"prompt 工程"层面拉到了"系统设计"层面：

> Agent 的记忆问题，不是 context window 大小的问题，而是**缓存一致性问题**。

当我们在设计一个 AI 编程助手的时候，我们默认了 Agent 读取的代码是"当前版本"。但 CI 会跑新测试、PR 会合入新代码、schema 会悄悄迁移。如果 Agent 的"记忆"没有失效机制，它就会在一个过期的世界上做决策。

**实践建议**：在构建长会话编程 Agent 时，引入外部状态的"最后验证时间"字段；超过阈值的状态必须 re-fetch，而不是依赖历史 context。这比扩大 context window 要有效得多。
