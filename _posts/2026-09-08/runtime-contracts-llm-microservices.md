## "能跑"和"可信"之间的距离

现在 AI 生成微服务的能力已经不是什么问题了。给定一个 spec，给定足够多的轮次修 bug，AI 能生成一个能通过测试的微服务。

但测试能跑，不等于在生产环境可信。分布式系统的实际问题都是运行时才暴露的：

- 延迟突刺时服务是否还能保持幂等？
- 降级策略是什么？数据边界在哪里？
- 依赖服务挂了，服务会不会"默默地"返回错误数据而不是报错？

这些问题在系统设计时就需要回答，但 AI 生成代码时不会主动声明它们。现有的做法是"生成之后人工 review 补上"，这实际上是拿 AI 做了最快的原型，然后靠人补设计。

## 运行时契约的本质

这篇论文提出的"运行时契约"是一组**可执行的形式化约束**，注入到 AI 生成的微服务里：

```
contract RuntimeContract {
  latency: P99 < 200ms  // 延迟约束
  idempotency: retry-safe  // 幂等性保证
  data_bounds: [min, max]  // 输出数据范围
  degradation: fallback_to_default  // 降级策略
}
```

关键设计：**契约失败不抛异常，而是触发预设的响应行为**——自愈重生成（重新生成更保守的实现）或人工接管（报警 + 暂停自动化流程）。

这个设计把"代码能不能跑"的验证从**编译期/测试期**挪到了**运行时**。这不是忽视形式化验证，而是在说：**有些约束在运行时验证比在编译期验证更务实**。

## 为什么是务实路线

形式化验证（formal verification）在学术上很漂亮，工程上有个致命问题：**它要求规格（spec）是完整的**。但 AI 生成系统的规格往往不完整——因为连设计者都不完全知道系统在所有边界条件下会怎么表现。

运行时契约的务实之处在于：

1. **不需要完整规格**——只需要声明关键边界（延迟、数据范围、幂等性）
2. **约束是可执行的**——不是文档，是代码
3. **失败有预设响应**——不会在生产环境裸奔

这相当于给 AI 生成的系统加了一层**运行时护栏**，而不是试图在生成阶段就穷尽所有验证。

## 对软件 3.0 架构的影响

"软件 3.0"的概念是 AI 生成大部分代码，人保留关键决策权。但这个模式要work，需要回答：**人在哪里介入，以什么形式？**

运行时契约提供了两种介入模式：

```
契约触发 → 人工接管（human-in-the-loop）
        → 自愈重生成（autonomous recovery）
```

自愈重生成的关键限制：它不能无限重试，必须有**退化为人工决策的明确出口**。否则系统可能在某个边界条件下无限 self-healing 而不报警。

## 和传统形式化方法的对比

| 维度 | 编译期形式化验证 | 运行时契约 |
|------|----------------|----------|
| 规格完整性要求 | 高（必须完整） | 低（只声明关键边界） |
| 验证时机 | 开发期 | 运行期 |
| 约束表达能力 | 强（完整逻辑） | 中（数据范围、延迟、幂等性） |
| 工程落地难度 | 高 | 中 |
| 对 AI 生成代码的适用性 | 低 | 高 |

这个对比很清楚：编译期形式化验证在 AI 生成代码这件事上，工程成本太高。运行时契约是一个**足够好的近似**，而不是理论上的最优解。

## 分布式环境下的"可信"含义

在分布式系统里，"可信"有具体的工程含义：

- **可观测性**：延迟分布、错误率、数据漂移能被监控
- **降级边界**：知道服务在什么条件下会fallback到降级策略
- **幂等性保证**：重试不会产生副作用
- **数据边界**：输出不会因为上游数据异常而越界

运行时契约实际上是在代码层面声明这些属性，然后在运行时强制执行它们。这是把架构设计文档变成了可执行的代码——"文档即测试，测试即运行"的一个务实变体。

## 总结

把形式化约束从编译期挪到运行时，是 AI 软件工程的务实路线。不是因为不想在编译期做验证，而是因为 AI 生成代码的规格不完整性决定了编译期验证成本过高。

运行时契约的核心价值：

1. **不需要完整规格**——关键边界声明就够了
2. **可执行、可监控**——不是文档，是护栏
3. **失败有预设路径**——不会裸奔
4. **人保留最终决策权**——自愈有上限，人工接管是保底

软件 3.0 的障碍不是"能不能生成代码"，而是"生成的东西在分布式环境下什么时候会失效、失效了怎么办"。运行时契约是回答这个问题的最小可行方案。
