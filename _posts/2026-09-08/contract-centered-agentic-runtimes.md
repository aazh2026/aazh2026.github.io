> 论文：*A Contract-Centered Architecture for Scalable and Manageable Agentic Runtimes*
> arXiv: [2608.27086](https://arxiv.org/abs/2608.27086)
> 作者：Yaxiao Liu et al.
> 备注：本文报告无已完成实现、实验或测量结果——这是一篇**架构论文**，提出假设和验证方案

## 为什么现有评估不够

一个 benchmark 能证明 Agent 完成了一个任务，但它无法回答：

- 变更模型时，业务行为是否还在预期边界内？
- 增加 10% 容量时，已 admitted 的 capability 语义是否保持？
- 安全策略的变更能否被正确追踪和验证？

换句话说，**任务成功率和企业级变更管理是两套不同的可观测性需求**，现有评估框架只覆盖前者。

## 四个责任对象

论文提出了四个共享的"组织契约"作为企业 AI 部署的责任边界：

| 对象 | 职责 | 本质 |
|------|------|------|
| **Skill** | 可复用、版本化的业务能力和工作流资产 | 业务行为的原子单位 |
| **Harness** | 运行时编译器 + 治理器 | Skill 的加载和执行环境 |
| **Scaffold** | 执行/控制边界 + NFR（非功能需求）所有者 | 容量、隔离、NFR 保证 |
| **Data Substrate** | Stack 外部的 CIO 治理语义和遥测基础设施 | 数据语义和血缘的独立保证方 |

运行时核心建模为 `A = <S, H, X>`（S=Skill, H=Harness, X=Scaffold），数据基础设施在这个栈之外。

这与"把数据也放在 Agent 栈内"的常见做法相反——作者认为数据语义必须独立治理，否则 Agent 可以悄悄改变数据的含义。

## 核心假设 P1：成本感知的能力-容量可分离性

这是论文最核心的科学贡献，一个**有界的、可证伪的假设**：

> **P1（成本感知能力-容量可分离性）**：在声明的操作区域内：
> 1. 变更激活的 capability，应在注册的双边等价边界内保持容量-响应交互
> 2. 变更兼容的 Scaffold 容量，应在注册的单向非劣边界内保持 capability 语义
> 3. 建立上述两点所需的控制，应保持在声明的执行预算内

翻译成人话：

- **换 Skill**（换个业务能力）不应该破坏容量边界（延迟、吞吐）——这是 Product Owner 的诉求
- **换 Scaffold**（增加容量）不应该改变业务语义——这是 Platform Owner 的诉求
- 两者都有**测量边界**，超出边界就是违约

六个设计条件成为可测量义务，其覆盖范围、违规情况、不确定性、成本和排除条款共同决定 P1 是否可判定。

## 四态判决

论文提出一个 cluster-period 随机交叉实验设计，判决结果有四种状态：

| 判决 | 含义 |
|------|------|
| **Supported** | P1 在操作区域内成立，变更受控 |
| **Falsified** | P1 不成立，变更边界不可控 |
| **Conditional-engineering** | P1 成立，但需要特定的工程条件 |
| **Inconclusive** | 数据不足，无法判定 |

这个实验设计最值得注意的点：**它不追求"通过/不通过"，而是要求实验者预先声明等价边界和非劣边界，然后看实际运行结果是否落在这个范围内。** 这把架构决策从"经验判断"变成了"可测量验证"。

## 对软件架构的冲击

### 从"框架"到"契约"

现有的 Agent 运行时讨论集中在"用什么框架"（LangGraph、AutoGen、LlamaIndex）。这篇论文的框架无关——它关心的是**任何运行时都必须回答的架构问题**：

- 谁拥有 Skill 的版本？谁可以升级？
- 谁拥有 Scaffold 的容量？谁可以扩容？
- 变更发生时，业务语义如何被验证？
- 数据血缘如何在 Agent 决策链中保持？

### 数据基础设施必须是 Stack 外部的

作者把数据基础设施明确放在 runtime stack 外部，由 CIO 独立治理。这有深刻含义：

> Agent 不能既是数据的消费者，又是数据语义的解释者——这违反了关注点分离原则。

对于构建企业知识管理 Agent 的团队，这意味着：知识库的 schema 变更必须独立于 Agent 的版本管理，Agent 不能自行决定数据血缘。

### 实用性警告

论文自己承认：**没有已完成实现、实验或测量结果**。这是一篇提出假设和验证方案的前瞻性架构论文，不是工程实践报告。P1 是否在实际系统中成立，目前未知。

## 价值所在

尽管没有实证，这篇论文的核心价值是它提出的**思考框架**：

企业 AI 部署不是"选一个 Agent 框架然后塞业务逻辑"，而是多租户、多团队、多变更速率的协调问题。**契约比框架更重要。**

Skill 契约：版本化、可复用、语义稳定
Harness 契约：运行时边界、可观测
Scaffold 契约：容量隔离、NFR 保证
Data Substrate 契约：数据血缘独立、CIO 治理

这个框架的每个要素都对应着企业实际出问题的点——只是目前还缺乏测量手段来验证 P1 是否成立。

## 总结：务实的架构研究方向

这篇论文提出了一个好问题：**企业级 Agent 运行时如何做到可验证的变更管理？**

它的答案框架性很强，但缺乏工程验证。对于从业者的意义是：

1. **把 Skill/Scaffold/Harness 的分离当作架构约束**——即使不用这个特定术语
2. **在设计阶段就声明变更边界**——等价边界和非劣边界，而不是上线后再发现语义漂移
3. **数据语义治理必须在 Agent 栈外部**——这是正确但经常被忽视的设计决策

P1 是否能在实际系统中证伪或支持，需要后续研究和工程验证。这篇论文提供了测量它的协议。
