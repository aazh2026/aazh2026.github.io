> 论文：*SKILL.state: Scalable Long-Horizon Agent Skills*
> arXiv: [2608.26263](https://arxiv/abs/2608.26263)
> 作者：Sanket Badhe, Priyanka Tiwari, Jonghyun Chung（Google LLC + Purdue University）

## append-only 是问题，不是特性

现有 Agent 运行时的共同模式：把观察、动作、中间推理轨迹不断追加到对话历史里。这导致两个根本问题：

- **延迟退化**：提示随执行历史线性增长，T=200 时标准 Prompt 运行时的提示长度达到 84,364 字符
- **上下文中毒**：无关历史积累稀释关键状态，高噪声场景下准确率从 0.68 降至 0.53

SKILL.state 的核心洞察：**append-only 历史不是维持状态的方式，而是状态管理失败的症状**。

## 核心设计：显式结构化执行状态

SKILL.state 将程序技能执行重新表述为**显式状态转换过程**。每个执行步骤定义为：

```
A_t = (P, Σ_t, O_t)
```

- **P**：不可变的程序规范（Skill 本身）
- **Σ_t**：步骤 t 时的结构化执行状态
- **O_t**：从环境接收的最新观察

执行流程：

```
1. 接收最新观察 Ot
2. 构建提示 (P, Σt, Ot)
3. LLM 生成 (Rt, ∆Σt, at)  // 推理 + 状态补丁 + 动作
4. 验证 ∆Σt
5. Σt+1 ← Σt ⊕ ∆Σt        // 应用状态补丁
6. 执行 at
7. 推理轨迹 Rt 丢弃        // 关键：不保留中间推理
```

推理轨迹 `R_t` 在状态转换验证后**永久丢弃**——它完成了当前步骤的推理职责，之后不再出现在提示里。

## 复杂度分析

| 运行时 | 提示长度 | 累计 token 复杂度 |
|--------|---------|-----------------|
| 对话式运行时 | O(t) — 随历史增长 | **O(T²)** |
| **SKILL.state** | **O(1) — 有界** | **O(T) — 线性** |

这是 SKILL.state 最重要的理论贡献：**O(1) 提示占用空间**。

## 关键实验数据

### 长期执行扩展性（Warehouse Management, Gemini-3-Flash）

| 范围 T | Runtime | 准确率 | 平均提示字符 | 总 Tokens |
|--------|---------|--------|------------|---------|
| 10 | Prompt (ReAct) | 0.90 | 3,249 | 9,438 |
| 10 | **SKILL.state** | **1.00** | **1,775** | **5,870** |
| 100 | Prompt (ReAct) | 0.84 | 36,362 | 1,245,413 |
| 100 | Stateful (LangGraph) | 0.91 | 31,354 | 1,062,387 |
| 100 | **SKILL.state** | **0.94** | **1,905** | **65,408** |
| 200 | Memory (Summary) | 0.84 | 84,364 | 6,175,509 |
| 200 | **SKILL.state** | **0.94** | **1,811** | **122,384** |

T=200 时，SKILL.state 准确率保持 0.94，而 Memory 消耗了 **6.1M tokens**——**50 倍差距**，且两者准确率相当。

### 高噪声（上下文中毒）鲁棒性

| 噪声级别 | Prompt | Memory | Stateful | **SKILL.state** |
|---------|--------|--------|---------|-----------------|
| 低（5事件） | 0.68 | 1.00 | 1.00 | **1.00** |
| 中（20事件） | 0.61 | 1.00 | 0.98 | **0.97** |
| 高（50事件） | 0.53 | 0.96 | 0.98 | **0.98** |

标准 Prompt 运行时在高噪声下从 0.68 降至 0.53，SKILL.state 在所有噪声水平下保持 ≥ 0.97。

### 预算匹配控制（T=100，~1,800 tokens 预算）

| Runtime | 准确率 | 总 Tokens |
|---------|--------|---------|
| Full ReAct（无界） | 0.84 | 1,245,413 |
| Truncated（滑动窗口） | 0.18 | 62,100 |
| ReAct + LLMLingua | 0.22 | 62,350 |
| **SKILL.state** | **0.94** | **65,408** |

统计压缩基线灾难性失败（0.18-0.22），而结构化状态维护保留了统计压缩器破坏的关键关系依赖。这说明**压缩不能替代结构化**。

### 公共基准测试（Gemini-3-Flash）

|------|------|--------|--------|---------|-----------------|
| InterCode CTF | Pass@1 | 43.2% | 46.4% | 41.8% | **54.2%** |
| InterCode CTF | 总 Tokens | 977k | 1.03M | 1.13M | **387k**（↓60.4%） |

## 局限与前提

论文坦诚地列出了 SKILL.state 失效的条件：

1. **状态充分性假设**：执行状态必须是对未来执行的充分统计量。当没有预先知道的固定模式、正确状态更新依赖早期观察、或任务目标定义在历史轨迹上时，SKILL.state 会失败。

2. **小模型错误分布**：开放权重模型 68% 的错误是过早状态覆盖/删除，20% 是模式理解问题——可通过约束解码改进。

3. **单代理实现**：多代理场景需要确定性冲突解决语义，当前未实现。

## 实践意义

SKILL.state 对工程实践的直接冲击：

1. **Agent 的状态不等于对话历史**：结构化执行状态（当前进度、待办项、环境事实）比 append-only 的观察序列更有价值
2. **推理轨迹不需要持久化**：中间推理的价值是生产当前状态更新，不是积累为未来的上下文负担
3. **统计压缩不如结构化**：滑动窗口和 LLMLingua 在 T=100 时准确率腰斩——压缩的是关系，不是 token
4. **有界提示是可能的**：O(1) 提示空间不是理论上限，是结构化设计的自然结果

对于构建长会话 Agent 的团队，这篇论文提供了比"扩大 context window"更根本的解决思路：**重新设计状态的表示和管理方式，而不是用更多 token 掩盖问题**。
