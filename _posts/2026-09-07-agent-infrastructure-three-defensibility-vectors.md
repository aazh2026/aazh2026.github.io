# AI Agent 基础设施的三个防御性拐点：可靠性、安全与自我改进

> 2026 年 6–9 月，三篇论文分别从三个方向封闭了 AI Agent 走向生产环境的最后几个漏洞。如果 Agent 要从「演示玩具」变成「企业级基础设施」，这三关必须过。

---

## 背景：Agent 的三层欠账

过去一年，LLM Agent 的能力边界被快速拓展——多步骤规划、工具调用、代码生成、跨仓库操作。但这些能力展示有一个共同的前提：**假设执行过程是可靠的、安全的、经验可积累的**。

这三个假设在真实生产环境里全部存疑：

- **可靠性**：Agent 执行到一半崩溃了，已执行的部分操作要不要回滚？金融操作双写怎么防止？
- **安全性**：单步安全检查无法捕捉跨步骤的累积风险，一个提示注入序列可能每步都看起来合规，组合起来却构成攻击。
- **可改进性**：这次 review 指出的错误，下一个会话里 Agent 还会再犯，因为它没有跨会话记忆。

三篇论文正好对应这三个欠账方向，各自给出了系统性的解法框架。本文不按论文分述，而是先说清每篇的核心洞察，再分析三者共同揭示的 Agent 架构趋势。

---

## 一、可靠性：ACID 事务引入 Agent 系统

**论文**：*Agentic Transaction: Towards ACID-Compliant Agent Systems*  
**作者**：Zhaoyan Sun 等，清华大学数据库组  
**时间**：2026-08-14  
**链接**：[arXiv:2608.13900](https://arxiv.org/abs/2608.13900)

### 核心问题：操作中途失败，谁来收拾残局？

数据库领域在 1980 年代就解决了这个问题——ACID 事务保证了一组操作要么全成功、要么全回滚，不会出现「钱扣了但货没发」这种中间状态。

但 Agent 执行和数据库事务有一个根本区别：**数据库事务的操作结果是确定的**，你可以精确地 commit 或 rollback；而 Agent 的每一步执行都有模型不确定性——同样一个「转账」操作，在不同状态下可能产生不同的副作用。

清华数据库组的核心贡献是把 ACID 语义**重新诠释**进了 Agent 执行的语义里：

| 数据库 ACID | Agent 语义重新诠释 |
|---|---|
| 原子性（Atomicity） | 语义原子性（Semantic Atomicity）：一组操作要么全成功，要么状态完全回滚，不留副作用 |
| 一致性（Consistency） | 语义一致性（Semantic Consistency）：最终状态满足预定义的不变量（invariants），而非只是「测试通过」 |
| 隔离性（Isolation） | 语义隔离（Semantic Isolation）：并发执行的多个 Agent 操作互不干扰，特别是对共享状态的修改 |
| 持久性（Durability） | 语义持久性（Semantic Durability）：操作结果可验证、可审计，不会因系统重启而丢失 |

具体实现上，他们构建了一个 **ACID-Compliant Data Agent**，核心机制包括：

- **事务性探索-执行-验证循环**：每个操作先探索（plan），再执行，再验证状态一致性，任何一步失败都触发回滚
- **事务性 Skill Hub**：将 Agent 的 skill 库也纳入事务管理，避免 skill 版本和执行状态不匹配
- **置信度分歧验证（Confidence Divergence-based Validation）**：用模型对当前状态的置信度和实际执行结果的对比来触发异常检测——当 Agent 自己对执行结果都没把握时，强制进入验证流程
- **语义依赖感知的隔离**：不同 Agent 的并发操作如果涉及语义相关的状态，强制序列化，而非只是锁机制

关键数字：在广泛使用的基准上，比包括 Claude Code 在内的最先进 Agent 提升了 **10.6%**。

### 这篇论文真正重要的地方

不是「让 Agent 有事务」，而是**示范了如何把数据库领域的经典理论映射到新的执行场景**。ACID 事务不是发明出来的，是移植过来的——这种跨领域的理论迁移，往往比纯经验性的工程优化更有生命力。

对于正在搭建 Agent 基础设施的团队，这篇论文提供了一个检查清单：你现在的 Agent 执行，有没有考虑语义原子性？状态验证依赖什么？不一致状态如何检测和回滚？

## 二、安全：从单步检查到轨迹级保障

**论文**：*Securing Agentic AI: From Per-Action Checks to Trajectory Assurance*  
**作者**：A Lotfi, Shanto 等  
**会议**：ACM AI Leadership Summit '26（Visionary Track）  
**链接**：[arXiv:2608.01558](https://arxiv.org/abs/2608.01558)

### 核心问题：每步都合规，整体就有害

传统的 Agent 安全方案是「每步操作前检查」：这个工具调用安全吗？这个文件写入允许吗？这个 API 请求合法吗？

这个框架在两个场景下会失效：

**场景一：提示注入（Prompt Injection）**  
攻击者在一封邮件里埋了一段隐藏指令，Agent 读取邮件时，单步检查看到的是「读取邮件内容」——完全正常；但这封邮件里藏着一段指令序列，引导 Agent 逐步泄露敏感信息。单独看每一步都合法，合在一起是一次数据泄露。

**场景二：多步骤累积危害**  
一个代码生成的 Agent，每步生成代码都是「合理的功能实现」；但 20 步之后，这 20 段代码组合起来引入了一个微妙的竞态条件或安全漏洞，单独看任何一步都没有问题。

论文的核心贡献是提出 **Trajectory Assurance（轨迹级安全保障）**：不再逐一审视每个动作，而是将 Agent 的**整个执行序列**视为一个整体来评估风险。相当于从「检查每个单词的拼写」升级到「检查整篇文章的逻辑一致性」。

具体而言，轨迹级安全要处理的问题横跨多个层次：

- **单 Agent 层**：来自 prompt、记忆、检索知识、工具接口的不可信输入构成攻击面
- **多 Agent 层**：跨 Agent 委托带来身份、信任、能力控制和决策透明度的挑战
- **基础设施层**：模型路由和执行控制面本身可能被操纵，模型来源未被验证
- **系统级**：供应链完整性、可追溯性、端到端可观测性基本是开放问题

论文最核心的原则陈述：**安全必须成为可验证的架构属性，而非可选的指导层。** 这是一个重要的范式转换——把安全从「配置项」变成「架构约束」。

### 为什么这篇论文的意义超出安全本身

它揭示了 Agent 系统的一个根本性改变：**安全的边界从单点变成了轨迹**。

在传统软件工程里，安全性可以通过输入验证、权限控制、API 限流等单点措施来保障。但在 LLM Agent 里，「输入」不再是一个清晰的边界——Agent 的输入是动态的、上下敏感的、嵌入在对话历史里的。安全策略必须跟着执行轨迹走，而不是跟着单个 API 调用走。

这意味着未来的 Agent 安全产品会向「轨迹审计」和「行为基线」方向演进——不是阻止某个调用，而是理解「这系列操作完成后，系统处于什么状态，是否符合预期」。

## 三、可改进性：跨会话行为规则积累

**论文**：*Self-Improving AI Coding Agents Through Accumulated Behavioral Rules: A Closed-Loop Framework*  
**作者**：Aditya Aggarwal, Nahid Farhady Ghalaty  
**会议**：32nd ICE IEEE/ITMC Conference (ICE 2026)  
**链接**：[arXiv:2607.13091](https://arxiv.org/abs/2607.13091)

### 核心问题：这次改对了，下次还犯

这是三个问题里最「软件工程」的一个。

LLM 驱动的编码 Agent 有一个根本性的记忆缺陷：它没有跨会话积累能力。用户在 code review 里告诉 Agent「这里不要用 `==` 比较浮点数，应该用 `math.isclose`」，Agent 当次修正了——但下一个会话，它还是一张白纸，遇到同类问题还会再犯。

这不是模型的问题，这是**架构的问题**：模型权重是固定的，人在 review 里传递的经验知识没有进入任何可积累的地方。

这篇论文的解法核心是**行为规则库（Behavioral Rules）**：

```
人类反馈 → 规则抽取 → 规则库积累 → 下次编码时检索应用
```

具体机制：
- **规则持久化**：每条被接受的 review 评论里蕴含的规则被抽取出来，写入一个版本控制的指令文件（不是模型权重，是显式的文本规则）
- **自检清单**：代码提交前，Agent 执行一个基于规则库的自检，而不是直接输出
- **规则完整性验证**：自动验证规则库的一致性，防止规则之间冲突或冗余
- **跨语言标准**：规则库里包含语言特定的编码标准（15+ 种语言特定规范）

部署效果（35+ 服务的微服务平台）：
- 规则库从 5 条增长到 18 条行为规则 + 15+ 语言标准 + 15 条自检清单
- 11 个真实工作会话（代码生成、PR review、故障调查、跨服务重构）里，**规则针对的错误类别实现了 0% 复发率**
- review 工作从「低层次正确性检查」转移到「设计层面的验证」

### 为什么这条路线比微调和 RAG 更聪明

对比现有方案：

| 方案 | 优点 | 缺点 |
|---|---|---|
| SFT 微调 | 知识固化进模型 | 成本高，不可回滚，无法解释 |
| RAG | 知识可更新 | 检索质量依赖，规则和上下文匹配不稳定 |
| **行为规则库** | **轻量、可审计、可编辑、不改权重** | **需要规则抽取的自然语言处理能力** |

这篇论文的核心洞察是：**经验知识不需要进入模型权重才能被利用**。行为规则是显式的、可文本审查的——用户可以直接读规则库，修改某条规则，删除某条规则，而不需要重新训练模型。这在企业场景里非常重要：合规团队需要能审查 AI 的决策依据，行为规则库提供了这个可能性。

## 三者的交汇：Agent 从「能力问题」变成「系统问题」

三篇论文有一个共同的主题：**AI Agent 的瓶颈正在从「模型能力」转移到「系统可靠性」**。

2024-2025 年的 Agent 研究主流是扩大模型能力边界——更长的上下文、更多的工具调用、更复杂的规划。但当能力边界足够宽之后，下一个问题浮现了：**能力边界够了，但系统不可靠、不安全、不能积累经验**。

这三个问题恰好是传统软件工程几十年积累的核心课题：事务处理、安全架构、持续改进。区别在于，这些传统课题在 LLM Agent 场景下需要重新诠释，因为 Agent 的执行不再是确定性的，而是概率性的——模型的输出有不确定性，状态转移不再像数据库那样可精确回滚。

清华的工作是把数据库事务理论「翻译」进 Agent 语义；Lotfi 等人的工作是把安全策略从「单点检查」升级到「轨迹保障」；Aggarwal 的工作是把软件工程的「持续改进」闭环引入 Agent 架构。

这三个方向合在一起，勾勒出一个清晰的方向：**Agent 基础设施的下一个战场不是模型，而是架构**。模型能力的差距会逐渐收敛，但事务保障、安全闭环和经验积累方面的架构差距会成为新的护城河。

## 对 Agent 开发团队的实践意义

**如果你的团队正在引入 AI 编码 Agent：**

1. **可靠性**：检查你现在用的 Agent 方案有没有「操作中途失败」的处理机制。如果没有，参考 ACID-Agent 的语义原子性和状态验证设计——至少要能在失败时回滚到一致状态。

2. **安全性**：单步权限检查是必要的但不充分的。你需要轨迹级的异常检测——特别是当 Agent 处理外部输入（邮件、文档、用户上传文件）时，要有关联的跨步骤审计。

3. **持续改进**：review 反馈到规则库的积累机制值得优先实现。这是一个低技术门槛、高回报的方向——不需要改模型，不需要重新训练，只要把 review 经验结构化存下来，下个会话就能用。

三篇论文的共同信号：**AI Agent 正在从「模型能力展示」阶段进入「系统工程保障」阶段**。哪个团队先在这三个方向上建立系统性解决方案，哪个团队就能在 Agent 生产部署的竞争中建立真正的壁垒。
